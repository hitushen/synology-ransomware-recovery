# 重启后救援案例（公开整理）

这是一份用于选择恢复路线的案例摘要。原始采集证据、私有日志、完整会话和恢复文件不公开；具体代数、偏移和设备号不能作为其他NAS的默认值。

- 受灾NAS已重启，DSM提示已重置，事先没有保存RAM。仍能通过既有、已授权的Telnet救援入口读取系统与存储状态，无需为取数据先重装DSM。
- 数据卷保持未挂载，底层为经核对的clean同代RAID1；通过范围限定的原始读取获取独立副本，再在分析机验证Btrfs超级块、元数据CRC和逻辑映射。
- 已试公共密钥候选与保存swap的指定布局，未取得匹配材料。阴性结果只代表测试过的范围，不支持所有会话都无法恢复的结论。
- 历史last_snapshot与超级块backup roots没有证明存在可用攻击前完整快照。旧extent路线仍有缺口，prev/next外推失败。
- 全卷目录盘点随后发现Synology Drive中的可达候选。大小/文件头仅用于筛选，最终使用完整范围关联、源块CRC、完整gzip/TAR流及独立回读SHA确认约57.24GB大备份。
- 归档完整与业务恢复分开：本轮没有证明备份制作时包含所有业务，也没有启动原容器或数据库进行业务验收。
- 一份虚拟磁盘无法完整原盘恢复时，改在受损副本解析客体ext4，抢救可验证的文件。部分目录名称未知，保留可逆编号，不把文件恢复称为可启动原VM或完整OVA。

公开资料见 [Solar工具接入](solar-tool.md)、[无密钥恢复](no-key-workflow.md) 与 [验收标准](export-verify.md)。
